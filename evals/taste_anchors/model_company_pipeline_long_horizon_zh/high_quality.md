# 八家模型公司的研发管线：平台、模型节点与任务回流

## 核心要点

1. 模型公司的管线通常由长期平台和一代模型节点组共同运转。长期平台维护数据、标注、训练 Infra、环境、评测、Serving 和发布能力；节点组冻结一代模型的能力目标、资源、版本与取舍，把平台能力组合成可交付系统。

2. 数据与标注贯穿预训练、中训、后训练和产品反馈。来源组合、质量评分、混合课程、人工规范、合成验证、环境轨迹与 lineage 形成一条数据链，训练团队通过消融和规模实验验收，产品失败继续修改任务定义与标注规范。

3. 预训练决定基座上限，中训提前注入代码、长上下文和 Agent 结构，后训练完成任务选择与行为塑形。三个阶段以 checkpoint、数据版本和评测版本交接；后训练无法稳定修复的缺口，会回到中训或下一代预训练。

4. Agent 时代的学习系统同时包含模型、环境和运行系统。环境启动、工具执行、验证器、轨迹完整性、新鲜度与重放决定学习信号质量，Coding Agent 又把 Harness、Serving、权限和成本纳入模型节点，交付物扩展为可回滚的配置束。

5. 模型公司A与模型公司B依靠专业团队获得纵深：A用模型节点负责人统筹数据、预训练和对齐，B把可靠性与部署门禁嵌入后训练。两者的共同代价是接口更多，版本与责任层必须清楚。

6. 模型公司C与模型公司G采用中央平台连接产品矩阵。C已形成稳定的平台—节点—产品分层；G只观察新负责人到任后的重组，Coding 场景承担中央基模与产品任务之间的首个共同接口。

7. 模型公司D用细粒度对照实验和客户场景评测连接训练与交付。待训团队参与标注，通用评测与场景评测构成两道发布门，优势是路线选择可归因，代价是实验吞吐和跨组协调成本较高。

8. 模型公司E、模型公司F与模型公司H都缩短了研究到交付的距离，路径并不相同。E依靠小型全链团队，F把算法与 Infra 共同扩展，H从新负责人到任后的首代节点起步，长期平台能否跟上多代并行仍有不确定性。

## 管线总览

完整管线围绕一个可复现的任务失败运转。任务先被归入知识、推理、代码、工具使用、长上下文、安全或效率等责任层，再确定该由数据、训练阶段、环境、Harness、Serving 或产品逻辑处理。每次模型节点都保留输入版本、实验结果和发布配置，因此线上失败能够回到具体批次，而非停留在“模型效果不好”的描述。

| 环节 | 长期责任实体 | 模型节点的决定 | 关键输入 | 交付与门禁 |
|---|---|---|---|---|
| 任务定义 | 产品、评测、数据研究 | 能力目标、优先场景、失败分类 | 真实任务、事故、客户反馈 | 可复现任务集与目标权重 |
| 数据与标注 | 数据平台、标注运营、数据研究 | 来源组合、规范、混合与课程 | 原始语料、专家规范、合成样本、环境轨迹 | 数据版本、质量报告、权利边界 |
| 预训练 | 预训练、架构、训练 Infra | 结构、token 预算、配方、规模路径 | 数据混合、算力、并行方案 | 基座 checkpoint 与消融结论 |
| 中训 | 领域训练、数据研究、评测 | 代码、长上下文、工具结构的注入比例 | 基座 checkpoint、领域数据、任务诊断 | 可进入后训练的中间 checkpoint |
| 后训练 | 对齐、RL、环境、奖励与安全 | SFT、偏好、奖励、RL、教师与蒸馏组合 | 任务数据、验证器、轨迹、策略版本 | 候选模型、策略与环境版本 |
| 评测 | 独立评测、领域评测、产品评测 | 发布阈值与失败归属 | 离线集、场景集、红队、成本与延迟 | 诊断卡、阻断项、回归集 |
| Serving 与发布 | 推理、平台、安全、产品 | 量化、路由、工具权限、回滚策略 | 模型、Harness、系统提示、工具清单 | 可部署配置束与回滚点 |
| 反馈回流 | 产品、数据、评测、节点负责人 | 进入本代热修或下一代训练 | 在线失败、人工复核、业务指标 | 新任务、新规范与下一代资产 |

这套分工的重点在于接口所有权。数据平台不能只按语料规模考核，它要对预训练和后训练中的增益负责；训练团队也不能把数据当作外部供给，而要提出缺口、参与规范并验收迁移效果。评测团队负责复现与归因，节点负责人负责跨环节取舍，平台负责人负责复用性和可靠性。独立考核仍可存在，但共同目标必须落到同一个模型节点和同一组任务结果。

## 八家公司对比

| 公司 | 组织原型 | 数据与标注 | 训练与 Infra | 评测、产品与发布 | 主要边界 |
|---|---|---|---|---|---|
| 模型公司A | 专业平台 + 模型节点 | 数据研究与预训练共同决定混合，标注规范跨阶段复用 | 预训练、对齐与平台专业化，节点负责人做版本取舍 | 评测卡随模型和推理配置交付 | 公开信息无法还原全部汇报线 |
| 模型公司B | 可靠性嵌入式专业团队 | 产品失败转成环境任务与回归数据 | 后训练、红队、Serving 共用发布门禁 | 高风险改动由训练、评测、部署联合确认 | 数据团队的组织归属不明确 |
| 模型公司C | 中央平台 + 多产品矩阵 | 中央数据平台维护来源、清洗和版本 | 中央 Infra 与基模团队掌握主版本 | 产品以任务单和在线失败返还，节点组跨平台取舍 | 决策升级路径未公开 |
| 模型公司D | 实验室式并行验证 + 交付场景 | 待训团队参与标注，规范与结果共同验收 | 关键选型由多组小实验、消融与规模验证决定 | 通用评测和客户场景评测构成双门 | 实验吞吐与人员成本缺少数据 |
| 模型公司E | 小型全链项目 | 研究员直接处理数据配方和轨迹 | 同一团队贯穿续训、RL、环境与推理优化 | checkpoint 到产品任务的回路短 | 扩大后存在关键人和平台深度风险 |
| 模型公司F | 算法—Infra 协同扩展 | 数据配方随结构和硬件共同验证 | 小规模消融后做跨规模、跨卡型迁移 | 发布同时考虑吞吐、稳定性和开放配套 | 内部所有权只部分可见 |
| 模型公司G | 负责人到任后的中央化重组 | 中央数据能力与产品任务重新连接 | 基模平台持有训练版本，产品持有 Coding Harness | Coding 场景成为首个共同任务接口 | 重组尚新，Harness 归属仍在变化 |
| 模型公司H | 负责人到任后的端到端首代节点 | 代码数据、人工规范、合成轨迹同节奏推进 | 节点组跨数据、训练和环境，复用既有 Infra | 发布模型、验证器、Harness 与 Serving 配置 | 多代并行后的稳定形态尚未得到验证 |

八家公司可以归入四种组织原型：A、B以专业化扩大深度；C、G以中央平台连接产品矩阵；E、H依靠全链节点缩短路径；D以细粒度实验和交付场景连接训练，F则以算法—Infra 协同为主轴。原型只能解释接口，不足以代替公司事实。公司G与H的结论严格从领导调整后的节点开始，旧组织不用于推断当前权责。

## 数据与标注

数据链的第一步是把真实任务变成可生产、可验收的任务分类。代码生成失败可能来自知识缺口、仓库检索、长程规划、工具调用、验证器误判或 Harness 上下文组织；这些失败需要进入不同数据池。任务分类完成后，数据团队组合授权语料、公开数据、专家样本、产品失败、合成样本和环境轨迹，并记录权利、成本、新鲜度、语言、领域、难度与污染风险。

生产管线可以压缩成九个相互约束的对象：任务分布与难度层；来源及权利；清洗、去重和质量评分；数据混合与课程；人工或专家规范；合成、批判和筛选；环境与轨迹；训练批次；版本 lineage 与归因。它们适合用表和版本记录管理。单看数据量或标注条数只能说明产能，无法说明某个任务是否改善，也无法区分高质量新信息与重复改写。

标注规范属于模型研发资产。规范要写清任务目标、允许的工具、正确性条件、部分得分、拒答边界和失败标签；专家负责定义难例与验收标准，运营团队负责稳定生产，数据研究负责抽样、分歧分析和噪声建模，训练与评测共同验证收益。模型公司D让待训团队参与标注，缩短了规范到训练的距离；模型公司C依靠中央平台提升复用；模型公司E和H把规范、合成和环境放入节点组，速度更快，跨代复用需要额外治理。

合成数据需要保留教师、提示、采样参数、批判器、验证器和过滤规则。环境轨迹还要记录工具版本、初始状态、执行日志、奖励分解、终止原因与重放结果。只保存最终答案会丢失可学习的行动结构，也无法区分模型错误、环境故障和验证器错误。新鲜度同样重要：依赖变化的仓库、网页、API 和工具任务必须按时间重建，陈旧轨迹会让训练学到已经失效的接口。

数据验收分三层。小规模受控实验确认方向和因果贡献；规模实验检查收益是否随模型与 token 预算保留；迁移实验检查换模型、换卡型、换环境或换 Harness 后是否仍有效。任何一层失败，数据版本都回到任务定义、规范或混合权重，而非用更多相似样本掩盖问题。

## 训练、Infra与评测

预训练、中训和后训练之间需要明确的 checkpoint 合同。合同至少包含模型与优化器版本、数据混合、token 预算、训练稳定性、已知能力缺口、污染检查、评测快照和可复现实验。中训负责把代码、长上下文、工具结构或领域能力放到后训练可利用的表示中；后训练通过 SFT、偏好、奖励模型、RL、教师和蒸馏选择行为。若一个缺口只能在固定评测上短暂改善，跨任务或跨环境立即回退，它不应被当作后训练闭环。

关键改动遵循“小实验—消融—规模—迁移”的升级顺序。数据、结构、训练目标和基础设施常常相互作用，单变量消融先识别贡献，再逐步扩大模型、数据和集群。模型公司D把不确定路线交给多组对照实验，模型公司F进一步检查跨卡型与跨规模迁移。集群规模会放大通信、检查点、数据加载和故障恢复中的小缺陷，Infra 的验收指标因此同时包含有效训练时间、故障恢复、数值一致性、成本与可追溯性。

评测体系至少有四层：稳定能力回归、任务诊断、真实场景、上线安全与效率。稳定回归用于阻止基础能力倒退；任务诊断把失败分到数据、训练阶段、环境或系统；真实场景由产品和交付维护，并保留代表性边界；上线门禁检查安全、延迟、吞吐、成本和回滚。模型公司B强调可靠性与部署联签，模型公司D采用通用与场景双门，模型公司C通过标准任务单连接产品矩阵。独立评测的价值来自阻断权和失败归因，单独维护排行榜没有同等作用。

发布对象包含模型权重或服务版本、tokenizer、系统提示、采样参数、路由、量化、工具清单、Harness、环境镜像、验证器、权限策略、评测快照与回滚点。只给模型版本号无法复现最终行为，也无法解释同一模型在不同产品中的差异。

## Harness与Coding Agent

Harness 出现前，代码训练往往围绕代码语料、单轮生成、单元测试和静态基准组织；模型调用工具的路径较短，评测主要关心答案或补丁。Coding Agent 把任务延伸到仓库理解、计划、检索、编辑、执行、调试和多轮恢复，模型性能开始强烈依赖上下文装配、工具协议、权限边界、环境可靠性和成本控制。

| 维度 | 代码生成阶段 | Coding Agent 阶段 |
|---|---|---|
| 数据单元 | 文件、函数、问答与补丁 | 仓库状态、工具调用、执行日志和完整轨迹 |
| 学习信号 | 参考答案、测试通过率 | 步骤奖励、验证器、重放、恢复能力与总成本 |
| 环境 | 可选沙箱 | 可启动、可重复、版本化的任务组成部分 |
| 评测 | 静态题与单轮补丁 | 长程成功率、污染、新鲜度、权限、延迟和失败归因 |
| Serving | 模型 API | 模型、Harness、路由、缓存、工具和权限的组合 |
| 发布 | checkpoint 与参数 | 可部署配置束、环境版本、验证器和回滚策略 |

Harness 团队与模型团队之间需要双向接口。Harness 负责把真实仓库任务转成稳定上下文、工具和执行环境，并报告上下文丢失、工具失败、恢复路径和成本；模型团队负责识别哪些失败属于表示、规划、动作选择或训练覆盖。模型公司G把 Coding 场景作为重组后的共同任务，平台持有模型版本，产品持有 Harness；模型公司H把 Harness 和环境纳入首代节点；模型公司E由全链研究员共同维护，接口少但复用风险更高。

Agent 训练产线的瓶颈常落在可用学习信号。环境启动失败、工具返回漂移、验证器奖励漏洞、轨迹截断和任务陈旧都会把系统噪声伪装成模型能力。有效做法是给环境、任务、Harness、验证器和策略分别版本化，失败先复现再归因，训练只接收可重放的轨迹。这样形成的资产既服务本代后训练，也能进入下一代中训、评测和产品回归。

## 不确定性

公开信息通常能确认团队是否存在、技术节点、招聘职责、发布流程片段和产品接口，很难完整确认汇报线、预算权、冲突裁决和人员实际流动。本研究因此把可确认的组织实体、流程接口与分析判断分开：模型公司A、B、F的内部所有权只有部分轮廓；模型公司G、H处于调整后的早期阶段，当前结构能否跨多代稳定运行仍待观察；模型公司D的实验吞吐和成本也缺少量化信息。

这些限制不妨碍比较管线，但会限制结论力度。四个结果可以作为跨公司的共同检验：任务失败能稳定复现并进入正确责任层；关键改动经得住消融、规模和迁移验证；模型节点交付可回滚的完整版本束；任务、环境、评测与事故沉淀为下一代资产。至于哪种组织原型长期更优，现有合成证据不足以给出统一排序。
